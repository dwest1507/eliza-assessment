# Research workspace (front-end)

The Next.js research workspace: an analyst asks a question, or clicks a starter prompt, watches the answer stream in, and clicks any `[Sn]` citation to open that Source's passage in a side panel. It sits on the stack of the developer's portfolio: Next.js (App Router), Tailwind CSS and the AI SDK's `useChat`. It shares the portfolio's look as well: a dark canvas with a faint grid and an ambient glow, glass cards, Inter with monospaced labels and a sky-blue accent, all defined as theme tokens and a few component classes in [`app/globals.css`](app/globals.css).

Run it from the repo root with `make dev`, which starts the chat API and this app together (see the root [README](../README.md#running-the-full-stack)).

## How it talks to the backend

The browser never calls the chat API directly. `useChat` posts the conversation to this app's own route, [`app/api/chat/route.ts`](app/api/chat/route.ts), which forwards the last messages the prompt uses (the question and the 10 before it, the backend's `HISTORY_TURNS`; older ones are dropped, so a long conversation keeps working), each with its role and text (and, for an earlier answer, the Filing ID each of its Source tags cited, never the passages) to the API's `POST /api/chat` (it reads them with the same helpers in [`lib/chat.ts`](lib/chat.ts) that the workspace uses to read a message's text, Sources and data parts) and streams the API's [AI SDK UI message stream](https://ai-sdk.dev/docs/ai-sdk-ui/stream-protocol) back unchanged. The API's URL therefore stays on the server. It comes from `BACKEND_URL` (copy [`.env.example`](.env.example) to `.env`); when unset it is `http://127.0.0.1:8000`, where `make api` listens. `make dev` sets it to the API it starts.

The stream carries the Query Scope and the numbered Sources as data parts before the answer text, so every citation is clickable while the answer is still arriving. Nothing else shows beneath an answer until it is complete (every answer is, except the last one while the chat is waiting for or streaming it; a restored answer always is), so the screen doesn't fill with chips before the text arrives. Then two collapsed disclosures follow it. "Sources (N)" lists only the Sources the answer cites, in tag order, and is left out when it cites none. "How this was answered" holds the Query Scope chips, so an analyst can see what the system answered and dispute it (each Sector phrase with the Companies it resolved to, hover for the Sector table rows it used; the other Companies, the time window, any Section hints and the metric), and every Source the Answer Call was given, cited or not. Each chip opens the Sources panel at its Source; the panel's switcher lists the cited Sources, plus the open one when it isn't cited.

An empty conversation shows the starter prompts and, below them, a line saying how many Companies are covered and how many have two or more years of quarterly Filings, linking to the "What's covered" list on "How it works". The workspace page builds those counts with [`lib/coverage.ts`](lib/coverage.ts) from the committed evaluation export's coverage grid, the data "How it works" reads, so the two pages never disagree; without that summary the workspace shows no coverage line.

The thread keeps the reader's place. Sending a question (typed, a starter or a follow-up) scrolls once, to put that question at the top of the thread, and the latest question and its answer always take at least the thread's height, so there is room for the answer below it. Nothing scrolls while the answer streams, so the reader can read its start while the rest arrives. A "Jump to latest" button shows while the end of the thread is below the visible area (an `IntersectionObserver` watches it) and scrolls there on click. A conversation restored after a refresh opens at its last question. Scrolling is smooth unless the user prefers reduced motion.

The conversation is kept in the browser's session storage ([`lib/conversation.ts`](lib/conversation.ts)), so a refresh keeps it and a new browser session starts empty; the backend keeps nothing. It is saved once each answer is complete. "New conversation" in the header clears it, so an old Query Scope can't leak into a new topic.

## Layout

| Path                               | What it is                                                                                            |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `app/page.tsx`                     | The workspace page, given the Corpus coverage summary from the evaluation export                      |
| `app/api/chat/route.ts`            | The server-side proxy to the chat API                                                                 |
| `app/how-it-works/page.tsx`        | The "How it works" page, rendered from the evaluation export                                          |
| `components/Workspace.tsx`         | The conversation thread, starter prompts and question box                                             |
| `components/AnswerMessage.tsx`     | One answer: Markdown with `[Sn]` citations as links, then its disclosures once it is complete         |
| `components/QueryScopeChips.tsx`   | The Query Scope chips, under an answer's "How this was answered"                                      |
| `components/Disclosure.tsx`        | A collapsed toggle that shows or hides its content                                                    |
| `components/SourcesPanel.tsx`      | The side panel showing one Source's Filing metadata and passage, or a Facts Source's table of figures |
| `components/AmbientBackground.tsx` | The portfolio's fixed, blurred background glow                                                        |
| `lib/chat.ts`                      | The stream's data part types, the shared message readers, the turn limit and the citation helpers     |
| `lib/starters.ts`                  | The six starter prompts, copied from the Brief Suite and the Golden Set                               |
| `lib/conversation.ts`              | Keeps the conversation in session storage                                                             |
| `components/HowItWorks.tsx`        | The architecture, the evaluation scoreboard and the coverage grid                                     |
| `components/TechnicalDetails.tsx`  | The "Technical details" layer: collapsible, linkable sections and the "Expand all" control            |
| `components/WhatsCovered.tsx`      | "What's covered": every Company, grouped by Tracked and Snapshot in plain words                       |
| `lib/coverage.ts`                  | The Corpus coverage summary (Company counts and list) built from the export's coverage grid           |
| `lib/evalExport.ts`                | The evaluation export's types and number formats                                                      |
| `data/eval-export.json`            | The evaluation export, written by `make eval-export` (committed)                                      |
| `__tests__/`                       | Vitest and React Testing Library tests                                                                |

The starter prompts are the labelled cases that carry a `starter` object, so every demo prompt is measured: the brief's three questions from the Brief Suite (`data/eval/brief_suite.json`), each taking over the starter of the Golden Set version 1 case it replaces, and three Golden Set cases (`data/eval/golden_set.json`). `__tests__/starters.test.ts` reads both files and fails if the copy in `lib/starters.ts` drifts from them.

## The "How it works" page

`/how-it-works`, linked from the workspace's header, puts the evidence inside the product: "What's covered" at the top (every Company, grouped in plain words into those with two or more years of history, the Tracked Companies, and those with only a few Filings, the Snapshot Companies, under the `#whats-covered` anchor the workspace's coverage line links to), the architecture (from the Corpus to the one Answer Call, and how it is measured), the evaluation scoreboard on Golden Set version 2 (each retrieval Arm against the Shipped Arm on Evidence Reached, with whether it can ship and the free screen's result; the shipped run beside its Control Run and each generator's scores, cost and latency; and the generator comparison: the Control Run's and each challenger's one-sided sign tests and bootstrap intervals against the shipped generator, and the generator chosen, worded as directional), the Brief Suite (each case's pass or fail, its missed must-state facts and how many never reached the Answer Context), the holdout run (its retrieval and answer scores, shown beside dev's with the small-sample caveat) and the Corpus coverage grid (each Company's Filings by Report Period, Tracked and Snapshot). The sections after "What's covered" sit under "Technical details", each collapsed by default and opened by clicking its heading; an "Expand all" / "Collapse all" control toggles them all, and a URL fragment naming a section's id (`#architecture`, `#scoreboard`, `#brief-suite`, `#holdout`, `#coverage`) opens it on load and whenever the fragment changes, so a link to the scoreboard lands on it open. On a wide screen the technical layer is wider than the reading column, so the tables fit; each table still scrolls sideways where the screen is too narrow. It is a static page built from [`data/eval-export.json`](data/eval-export.json), which `make eval-export` writes from the harnesses' latest reports (see the root [README](../README.md#showing-the-results-in-the-workspace)). The file is committed and generated, never edited by hand; Prettier skips it.

## Commands

From the repo root, `make install`, `make test`, `make lint` and `make format` cover this app as well as the backend. Inside `frontend/`:

| Command                                                       | What it does                                                    |
| ------------------------------------------------------------- | --------------------------------------------------------------- |
| `npm run dev`                                                 | The dev server on http://localhost:3000 (needs the API running) |
| `npm test`                                                    | The Vitest suite                                                |
| `npm run lint` / `npm run typecheck` / `npm run format:check` | ESLint, TypeScript and Prettier checks                          |
| `npm run build`                                               | A production build                                              |

The tests run against a mocked stream: `fetch` returns the API's UI message stream, so the real `useChat` parses it. A controllable variant holds the stream open after a chosen part, so a test can see an answer in progress. They cover a starter sending on click, Markdown rendering, a citation opening its Source in the panel (while the answer streams too), nothing shown beneath an answer until it is complete, "Sources (N)" listing only the cited Sources, "How this was answered" holding the Query Scope chips and every retrieved Source, the panel's switcher, a cited tag that isn't among the Sources shown as unavailable, a Facts Source shown as a table, the conversation surviving a refresh with its disclosures, the "New conversation" control, the scrolling (`__tests__/WorkspaceScroll.test.tsx`, which stubs the scroll, motion and visibility APIs jsdom lacks: one scroll on send and none while the answer streams, a restored conversation opening at its last question, and "Jump to latest" showing, scrolling and hiding), the API's reason shown when it rejects a request, the empty workspace's coverage line and its link (and no line without the coverage summary), the proxy route (which sends only the turns the prompt uses), and the shared message readers (the cited Sources among them) and turn limit (`__tests__/chat.test.ts`, which also checks the front-end's copy of the prompt's `HISTORY_TURNS` against the backend's). The "How it works" page, including the grouped "What's covered" list, is rendered from a fixture export (`__tests__/fixtures/eval-export.json`); its tests open each technical section by its heading before reading it, and cover the sections starting collapsed, "Expand all" and "Collapse all", and a URL fragment opening its section.
