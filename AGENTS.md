# AGENTS.md

## Agent skills

### Issue tracker

Issues are tracked in GitHub Issues (dwest1507/eliza-assessment) via the `gh` CLI. See `docs/agents/issue-tracker.md`.

### Triage labels

Default labels: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`. See `docs/agents/triage-labels.md`.

### Domain docs

Single-context: one root `CONTEXT.md` plus `docs/adr/`. See `docs/agents/domain.md`.

## Repo layout and commands

- `backend/`: uv-managed Python project holding the `edgar_rag` core package (`src/`), its tests (`tests/`) and the EDA notebook (`notebooks/`). The core package must not depend on a web framework.
- `frontend/`: the Next.js research workspace (npm-managed; Tailwind, AI SDK `useChat`, Vitest). Its server-side route `app/api/chat/route.ts` proxies to the backend's chat API, so the backend URL (`BACKEND_URL`) stays on the server. The conversation lives only in the browser's session storage (`lib/conversation.ts`); the backend is stateless. `lib/starters.ts` copies the starter prompts of the Golden Set and the Brief Suite, and `lib/chat.ts` copies the prompt's `HISTORY_TURNS` (the proxy sends at most that many earlier messages, and the API rejects more); a test keeps each copy in sync. The "How it works" page (`app/how-it-works/page.tsx`) renders the committed evaluation export, `data/eval-export.json`, typed by `lib/evalExport.ts`. See `frontend/README.md`.
- `data/edgar_corpus/`: the Corpus, read-only (see `data/README.md`). Derived files go in `data/derived/` (gitignored).
- `data/reference/sectors.csv`: the curated Sector table, one row per Company (see `data/README.md`).
- `data/reference/missing_companies.csv`: the curated list of notable Companies not in the Corpus, named as Coverage Gaps (see `data/README.md`).
- `data/eval/golden_set.json`: the Golden Set, the evaluation's labelled questions, including three of the front-end's starter prompts (see `docs/golden-set.md`). Its tests check every label against the Corpus. Version 1's file stays unchanged as a record (a test pins its digest).
- `data/eval/golden_set_v2.json`: Golden Set version 2, holding so far the first 18 of version 1's 27 non-brief cases, rewritten (`docs/golden-set.md`, "The rewritten version 1 cases"). Same schema, every fact tiered, and each case records its split: `dev`, `holdout` or `pending` until the split is frozen. The harnesses run version 1 unless `--golden-set` names this file, and refuse a set with a pending case. The same label tests cover it, plus repeated questions across the three files, figure facts against the SEC company-facts reference (skipped without the cache), and its mix of question kinds against ADR 0012 (reported, not enforced). See `docs/golden-set.md`, "Version 2".
- `data/eval/brief_suite.json`: the Brief Suite, the brief's example questions and variants of them outside the dev/holdout split (a must-pass check), with the other three starter prompts. Same schema, no split, every fact tiered; `replaces` names the version 1 case a case was rewritten from, and `variant_of` the brief question a variant varies. The same label tests cover it (see `docs/golden-set.md`, "The Brief Suite").
- `data/eval/judge_study/`: the judge study's labelling sheet and sample, hand-made labels and so committed (see its README). Its verdicts and score stay in `data/derived/judge_study/`.
- `backend/src/edgar_rag/`: `corpus.py` (the Corpus seam), `financial_facts.py` (the Financial Facts seam), `retrieval.py` (the retrieval seam: build the index, prepare an Answer Context), `answer_model.py` (the answer model protocol and the logged Answer Call), `sec_reference.py` (fetches and reads the SEC company-facts evaluation reference), `golden_set.py` (loads and validates both Golden Set versions and the Brief Suite, computes version 1's dev/holdout split, reads version 2's recorded one and refuses a run while a case is pending, and merges the starter prompts), `paths.py` (the data directory, defined once: every backend module builds its `data/` paths from it, never from its own file location, and a guard test enforces it). The Query Scope parser and follow-up inheritance (ADR 0003) live in the internal `_query_scope.py`. Standard library only; a guard test enforces it.
- `backend/src/edgar_answer/`: code that needs a provider SDK, kept outside the core package (ADR 0005): `openai_model.py` (the shipped generator), `anthropic_model.py` (the Claude generators, for the generator comparison only) and `ask.py` (`make ask`).
- `backend/src/edgar_api/`: the FastAPI chat API (`app.py`, `make api`), outside the core package: `POST /api/chat` streams the AI SDK UI message stream (Query Scope and Sources as data parts, then the answer), `GET /api/health`. Stateless. `backend/scripts/chat.sh` is the `curl` example.
- `backend/src/edgar_eval/`: the evaluation harnesses, kept outside the core package (ADR 0006): `retrieval.py` (the retrieval harness, `make eval-retrieval`, with its gate and free screen on Evidence Reached), `arms.py` (every retrieval Arm, one marked shipped; each runs the retrieval seam with its own ranker), `rankers.py` (the challenger Arms' rankers: dense, hybrid, cross-encoder), `embeddings.py` (chunk embeddings for the dense and hybrid Arms, `make embeddings`), `metrics.py` (hit@k, recall@k, MRR, McNemar's exact test, the sign test with its one-sided p-values, the bootstrap interval, and the judge study's Cohen's kappa, Wilson interval and Fisher's exact test), `selection.py` (the selection rules that pick the Shipped Arm, `make eval-arms`, the generator, `make eval-generators`, and the chunk size and context budget, `make eval-settings`; how the rules differ is stated once, in `RULES`, and the one pair of thresholds every rule uses once, in `AHEAD_P` and `BEHIND_P`; every comparison has a Control Run, and the comparisons of one round share one shipped run and one Control Run), `generation.py` (the generation harness, `make eval-generation`; `make eval-rescore` redoes its figure check on the saved reports offline), `brief_suite.py` (the Brief Suite run through that harness, `make eval-brief`: several runs a case, a pass/fail verdict per case, and the cost estimate every paid run prints first), `generators.py` (`GENERATORS`, the one table of compared generators with each one's provider and price: the answer cost, the harness's answer model, the `make eval-generators` list and the Makefile's API-key check all read it, so adding or repricing a generator is one edit), `answer_checks.py` (citation, figure, Coverage Gap and answer-structure checks in code), `judge.py` (Fact Recall and Faithfulness by Jev, pinned in `JEV_MODEL`, a fact counting as stated from `FACT_CUTOFF`), `judge_study.py` (the judge study of ADR 0013: `make judge-study-sample` draws its items from the saved reports with a fixed seed and writes the blind labelling sheet, `make judge-study-judge` has Jev judge them twice and, with `LLM_SPLIT=1`, runs the trial LLM claim split, and `make judge-study-score` scores the verdicts against the labels and compares the two claim splits), `export.py` (the evaluation export for the front-end, `make eval-export`).
- `docs/evaluation.md`: how quality is measured and the scores: each harness's method and its first numbers on dev.
- `docs/findings.md`: EDA findings, each as Finding → Implication → Design decision, ending with recommendations for the retrieval phase.
- `docs/assumptions.md`: every assumption we build under, each marked `confirmed` or `not confirmed` by the Client. `docs/client-email.md` (gitignored, local only) is the email the developer sent the Client about the three that matter most (1, 2 and 3), and the Client's reply confirming them. An agent never sends email to the Client.
- `docs/prompt-iterations.md`: every version of the Answer Call's prompt template. A change to `backend/src/edgar_rag/_prompt.py` bumps `PROMPT_VERSION` and adds an entry.
- `docs/deck.md`: the slide deck, Marp Markdown with speaker notes in HTML comments. Each slide links the documents its numbers come from, and `backend/tests/test_deck.py` checks every figure on a slide appears in one of them; update the slide when an evaluation number changes.
- `docs/adr/`: architecture decisions, numbered `NNNN-slug.md` (0001: the SQLite Financial Facts store; 0008: the Arm comparison and the Shipped Arm; 0009: the generator comparison; 0010: the chunk size and context budget; 0011: the decision thresholds and the Control Run; 0012: Golden Set version 2 and the Brief Suite; 0013: Jev stays the judge, checked by a judge study). ADRs 0011 to 0013 are decided but not built yet (built so far: tiered Required Facts, the Brief Suite, Golden Set version 2's file with a split per case, some measurement fixes, the one-sided thresholds, the Control Run, and the judge study's sample, judging, score and trial LLM claim split), and the harnesses still run Golden Set version 1 under the rules of 0008 to 0010 (`docs/evaluation.md`, "Evaluation version 2").

Run everything through the root `Makefile`: `make install` (uv sync and npm ci), `make test`, `make lint`, `make format` (each covers the backend and the front-end), `make eda`, `make sec-facts`, `make index`, `make embeddings`, `make ask Q="..."`, `make api`, `make eval-retrieval`, `make eval-generation`, `make eval-brief`, `make eval-rescore`, `make eval-arms`, `make eval-generators`, `make eval-settings`, `make eval-export`, `make judge-study-sample`, `make judge-study-judge`, `make judge-study-score`, `make deck` (renders the slide deck with the Marp CLI via `npx`), `make dev` (the API and the front-end together; stops both if either exits).

`make index` rebuilds the retrieval index, `data/derived/edgar_rag.sqlite`, from the Corpus, in 600-token chunks (`CHUNK_TOKENS`; the context budget is `CONTEXT_BUDGET_TOKENS`, 32k, both in `edgar_rag.retrieval` and chosen in ADR 0010). `make ask` answers one question through one Answer Call (it needs `OPENAI_API_KEY` from `backend/.env`, and costs money) and logs it to `data/derived/logs/answer_calls.jsonl`. `make api` serves the same pipeline on port 8000 (`API_PORT` overrides); its tests use FastAPI's test client. Tests never call a provider: they use a fake answer model.

`make eval-retrieval` scores every retrieval Arm on the Golden Set's dev split (`SPLIT=holdout` or `SPLIT=all` to change it; `ARMS="fts5 rerank"` to run only some) with no LLM call, and writes the report to `data/derived/eval/retrieval-<split>.json`. `CHUNK_TOKENS=450` and `CONTEXT_BUDGET=24000` (on it and on `make eval-generation`) score another chunk size or context budget without editing code: `CHUNK_TOKENS` builds `data/derived/edgar_rag-chunks<N>.sqlite` when missing, the report's name gains the setting, and every report records both (use `ARMS=fts5` with `CHUNK_TOKENS`, since the embeddings belong to the shipped index). Its "evidence" column counts the Required Facts whose evidence quote reaches the Answer Context, and the report records Evidence Reached per Required Fact. It gates each challenger Arm on it (McNemar's exact test, paired per fact, one-sided, under the selection rules' thresholds; hit@k, recall@k and MRR are reported, not gated on) and screens the challengers: a candidate goes on to paid Answer Calls only if Evidence Reached does not put it behind the shipped choice at one-sided p < 0.20, at most three go on, the most Evidence Reached first and the fewest Source tokens on a tie (ADR 0011). `make eval-arms` and `make eval-settings` apply the screen before their paid runs, and their choice files record it. Tune on dev only; the holdout is scored once per final setup and never used to choose (`docs/evaluation.md`, "The holdout rule"): a run on it reports and decides nothing, and nothing changes after it. It has been scored on the setup that ships (`docs/evaluation.md`, "The holdout run"), so score it again only if a dev choice changes what ships, and never to tune a choice. The dense and hybrid Arms read chunk embeddings that `make embeddings` builds once into `data/derived/embeddings/` (OpenAI `text-embedding-3-small`; needs `OPENAI_API_KEY`, costs about 35 cents, and resumes if stopped); their question embeddings are cached there too, so reruns make no call. The rerank Arm downloads its cross-encoder once from Hugging Face, pinned to a commit. The challengers' packages (numpy, ONNX Runtime, `tokenizers`, `huggingface-hub`) are in the backend's dev dependency group only, and a guard test keeps them out of the product.

`make eval-generation` answers the same split through real Answer Calls and scores the answers (checks in code, Jev judgments, cost and latency), writing `data/derived/eval/generation-<split>.json`. It needs `OPENAI_API_KEY` and `JEV_API_KEY` from `backend/.env` and costs money (about $0.07 per dev run), so run it only when a change to the prompt, retrieval or generator needs scoring. `ARM=dense` answers through another retrieval Arm, writing `generation-arms-<split>-<arm>.json`. `make eval-brief` runs the Brief Suite through the same harness: each case answered 5 times (`RUNS=` changes it; `MODEL=`, `ARM=`, `CHUNK_TOKENS=` and `CONTEXT_BUDGET=` as for `make eval-generation`), passing when every must-state Required Fact is stated in at least 4 of the 5 runs and no run has a Contradicted Claim, reported case by case with each fact's Evidence Reached, and written to `data/derived/eval/brief-suite.json`. It needs the same keys and costs money (about $0.30 for its 75 Answer Calls with `gpt-6-luna`); like every generation run it prints its estimated cost before the first Answer Call. `make eval-rescore` redoes the figure check of every saved generation report from its stored answers, in place: it prepares each Answer Context again, at the context budget the report records (it refuses a report from an index of another chunk size, and a case whose Sources no longer match) and makes no Answer Call and no Jev call, so it is free and allowed on the holdout, since it fixes a measurement and changes no choice. `make eval-arms` runs the retrieval harness first (free, writing `retrieval-<split>.json`), answers the split through the Arms its screen keeps, and applies the selection rule (`edgar_eval.selection`, ADR 0011: a challenger ships only if the one-sided sign test puts it ahead on Fact Recall at p < 0.10 and behind on no guardrail, Faithfulness, Coverage Gaps or Contradicted Claims, at p < 0.20; the cheapest qualifying challenger wins; each score also reports the mean paired difference with a 95% bootstrap interval, fixed seed, shown but not decided on; version 1's choice files, made at two-sided p < 0.05, are records and are not recomputed), writing `arm-choice-<split>.json`; it costs about $0.07 per Arm on dev. Every comparison also has a Control Run, the shipped choice run again: if it comes out ahead of the shipped run on one of the rule's ahead metrics, the choice is inconclusive and the shipped choice stands. `make eval-arms`, `make eval-settings` and `make eval-generators` share one round's shipped run (`generation-<split>.json`) and Control Run (`generation-control-<split>.json`), reusing them while the code (a digest of `backend/src/`), prompt and Golden Set version the reports record are unchanged and running them first otherwise, so a round's first comparison costs about $0.14 more. `make eval-settings CANDIDATES="450:32000 600:48000"` screens the shipped setting and each named chunk size and context budget with the retrieval harness first (free, writing `retrieval-<split>-chunks<N>-budget<B>.json`), answers each setting the screen keeps and applies the Arm rule, writing `generation-<split>-chunks<N>-budget<B>.json` and `settings-choice-<split>.json`. `MODEL=claude-sonnet-5-5` answers with another generator (a model's provider, and so the key it needs, `OPENAI_API_KEY` or `ANTHROPIC_API_KEY`, comes from `edgar_eval.generators.GENERATORS`; a model not in that table is refused), writing `generation-<split>-<model>.json`. `make eval-generators` answers the split with `gpt-6-luna` and `claude-haiku-5-5`, version 2's comparison, and applies the generator rule (a challenger replaces `gpt-6-luna` only if ahead on Fact Recall or Coverage Gaps and behind on none of Fact Recall, Faithfulness, Coverage Gaps and Contradicted Claims, at the same thresholds), writing `generator-choice-<split>.json`; it costs about $0.15 on dev. `MODELS="..."` names other generators from the table instead (`gpt-6-luna` always runs, as the shipped one), and `MODELS=` (empty) runs every one, version 1's four included, for about $6 on dev; the version 1 generators stay in the table so their reports still price. Jev stays pinned to an exact version, never `jev-latest`; a new version is a deliberate change that re-baselines every score.

`make eval-export` writes the latest reports of a split (`SPLIT=`, dev by default; with the generator comparison and, beside dev, the holdout's reports) and the Corpus coverage grid to `frontend/data/eval-export.json`, which the "How it works" page renders. It runs the retrieval harness when its report is missing, never the generation harness. The export is committed: regenerate it with `make eval-export`, never edit it by hand, and keep its shape in step with `frontend/lib/evalExport.ts` (the type check fails when they drift).

`make judge-study-sample` draws the judge study's items (ADR 0013) from every saved generation and Brief Suite report: 150 (answer, Required Fact) items, using only the rewritten one-claim facts of Golden Set version 2 and the Brief Suite, never version 1's compound ones, and 200 (claim, cited Sources) items re-split from the stored answers, over-sampling uncertain probabilities, unsupported and contradicted verdicts, and every generator. It draws with a fixed seed (`SEED=` changes it) and writes `data/eval/judge_study/sheet.md`, the blind labelling sheet the developer fills in, with no Jev verdict or probability in it, and `sample.json` beside it, which records why each item was drawn and is not read while labelling. Both are committed, beside the Golden Set, since they hold hand-made labels; the developer commits the labelled sheet. No drawn sheet is committed until version 1's cases are rewritten. It calls no provider and is free; running it again keeps every label entered, and refuses to drop a labelled item. See `docs/evaluation.md`, "The judge study's sample".

`make judge-study-judge` has Jev judge every sampled item twice (`REFERENCE=1` adds Claude Haiku 5.5 once, as a reference judge; `LLM_SPLIT=1` adds the trial LLM claim split, Claude Haiku 5.5 splitting each sampled answer into one-claim statements, cached per answer in `data/derived/judge_study/llm_split/`, which Jev judges once; it lives in the study only, never in the generation harness), printing the estimated cost first; it needs `JEV_API_KEY` (and `ANTHROPIC_API_KEY` for the reference or the split) and costs money, so run it only with the developer's approval. It writes `data/derived/judge_study/verdicts.json` (gitignored, since it can be regenerated), apart from the sheet, with a verdict or a recorded failure for every item in every run. `make judge-study-score` is free: it scores those verdicts against the sheet's labels (accuracy and kappa, the share of bad claims called supported, error by generator, run-to-run agreement, the fact cut-off sweep, ADR 0013's revisit trigger, the early-stopping rule and, when the split was run, which split's claims agree better with the labels, answer by answer) and writes `score.json`; it refuses while items are unlabelled unless the stopping rule is met or `PARTIAL=1`. The fact cut-off is `FACT_CUTOFF` in `edgar_eval.judge`, 0.5 until the study sets it, and every generation report records it. See `docs/evaluation.md`, "Judging and scoring the judge study".

`make sec-facts` caches the SEC XBRL company-facts data (an evaluation reference for Financial Facts, never an answer source) in `data/derived/sec_companyfacts/`; `make eda` runs it when that cache is missing. The SEC requires a User-Agent with a contact email, read from the `SEC_USER_AGENT` environment variable, which the Makefile loads from `backend/.env`.

Environment files are per app: each app has a gitignored `.env` and a committed `.env.example` with placeholders only, and the app's `.dockerignore` keeps `.env` out of images. The developer fills in `.env`; an agent never creates or edits it and never writes a real value into code, the Makefile, docs, tests, notebook outputs, `.env.example` files or commit messages. A new variable goes into that app's `.env.example` with a placeholder.

The notebook source of truth is `backend/notebooks/eda.py` (jupytext percent format). `make eda` executes it and writes the paired `eda.ipynb` with outputs; commit both and never edit the `.ipynb` by hand.
