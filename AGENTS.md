# AGENTS.md

## Agent skills

### Issue tracker

Issues are tracked in GitHub Issues (dwest1507/eliza-assessment) via the `gh` CLI. See `docs/agents/issue-tracker.md`.

### Triage labels

Default labels: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`. See `docs/agents/triage-labels.md`.

### Domain docs

Single-context: one root `CONTEXT.md` plus `docs/adr/`. See `docs/agents/domain.md`.

## Repo layout and commands

- `backend/`: uv-managed Python project holding the `edgar_rag` core package (`src/`), its tests (`tests/`) and the EDA notebook (`notebooks/`). The core package must not depend on a web framework.
- `frontend/`: the Next.js research workspace (npm-managed; Tailwind, AI SDK `useChat`, Vitest). Its server-side route `app/api/chat/route.ts` proxies to the backend's chat API, so the backend URL (`BACKEND_URL`) stays on the server. The conversation lives only in the browser's session storage (`lib/conversation.ts`); the backend is stateless. Each answer's Coverage Gaps show below it as Coverage notes once it is complete, never above it (`components/CoverageGaps.tsx`, ADR 0016). `lib/starters.ts` copies the starter prompts of the Golden Set and the Brief Suite, `lib/chat.ts` copies the prompt's `HISTORY_TURNS` (the proxy sends at most that many earlier messages, and the API rejects more), `lib/followUps.ts` copies the company-name shortening of `_query_scope.py` (`_SUFFIX`, `_THE` and `short_name`, so a suggested follow-up names a Company as the rules match it), and `lib/source.ts` copies the passage gap marker `GAP` of `_repeats.py` (retrieval writes it only where a Source skips text, since chunks next to each other in a Filing join as one passage with their overlap shown once; the Sources panel shows it as "passage skipped" and spaces sentences the Corpus glued together, on display only); a test keeps each copy in sync. The "How it works" page (`app/how-it-works/page.tsx`) renders the committed evaluation export, `data/eval-export.json`, typed by `lib/evalExport.ts`: a plain overview first (`components/Overview.tsx`), then "Technical details", which shows exactly three sections, each with only the latest results: the architecture, the evaluation scoreboard (retrieval for every Arm, the latest round's shipped run beside its Control Run, and that round's generator comparison) and the latest holdout run (no Brief Suite, no earlier rounds' comparisons, no Corpus coverage grid; `docs/evaluation.md` keeps the history). The workspace page reads the same export's Company Calendars (`companies`) for the empty screen's coverage line (`coverageSummary` in `lib/coverage.ts`), which links to that page's "What's covered" search, and for the side panel's Calendar tab (`components/CalendarPanel.tsx`: a ticker tab per Company any answer's Query Scope named, alphabetical, each showing its `components/CompanyCalendar.tsx`, the component "What's covered" shares). "What's covered" (`components/WhatsCovered.tsx`) searches the export's `companies` by name, ticker and common names (`commonNames`, from the Query Scope parser's alias table via `common_names`, so it matches what questions understand) and its `missingCompanies`; a card's "Ask about this company" opens the workspace at `/?ask=<question>`, which fills the question in without sending it (`lib/coverage.ts`). See `frontend/README.md`.

Its tests check every label against the Corpus. Version 1's file stays unchanged as a record (a test pins its digest); a harness runs it only when `--golden-set` names it.

Same schema, every fact tiered, and each case records its split. The split is frozen (`docs/golden-set.md`, "The frozen split"): the 20 new cases with the lowest SHA-256 id digests are `holdout`, every other case `dev`, so 60 dev and 20 holdout at the freeze (63 dev with the cases added later), none `pending`; the file lists the holdout ids (`holdout_ids`), the loader refuses any recorded split that disagrees with that list, and a case added later is `dev` unless a new Golden Set version says otherwise. It is the harnesses' default (`DEFAULT_GOLDEN_SET`), and a harness refuses a set with a pending case. The same label tests cover it, plus repeated questions across the three files, figure facts against the SEC company-facts reference (skipped without the cache), the frozen split recomputed from the digests, and its mix of question kinds against ADR 0012 (reported and pinned as frozen, not adjusted). See `docs/golden-set.md`, "Version 2".

Run everything through the root `Makefile`: `make install` (uv sync and npm ci), `make test`, `make lint`, `make format` (each covers the backend and the front-end), `make eda`, `make sec-facts`, `make index`, `make embeddings`, `make local-embeddings`, `make ask Q="..."`, `make api`, `make eval-retrieval`, `make eval-generation`, `make eval-brief`, `make eval-rescore`, `make eval-misses`, `make eval-arms`, `make eval-generators`, `make eval-settings`, `make eval-export`, `make judge-study-sample`, `make judge-study-judge`, `make judge-study-score`, `make human-check-sample`, `make human-check-score`, `make deck` (renders the slide deck with the Marp CLI via `npx`), `make dev` (the API and the front-end together; stops both if either exits).

`make index` rebuilds the retrieval index, `data/derived/edgar_rag.sqlite`, from the Corpus, in 600-token chunks (`CHUNK_TOKENS`; the context budget is `CONTEXT_BUDGET_TOKENS`, 32k, both in `edgar_rag.retrieval` and chosen in ADR 0010). `make ask` answers one question through one Answer Call with the answer model `ANSWER_MODEL` names (it needs that model's provider key from `backend/.env`, `OPENAI_API_KEY` for the default, and costs money; it says when the answer stopped at the token cap) and logs it to `data/derived/logs/answer_calls.jsonl`. `make api` serves the same pipeline on port 8000 (`API_PORT` overrides), with the same `ANSWER_MODEL`, refusing at start-up a model not in the table and logging a warning for every answer that stops at the token cap; its tests use FastAPI's test client. Tests never call a provider: they use a fake answer model.

`make eval-retrieval` scores every retrieval Arm on the Golden Set's dev split (`SPLIT=holdout` or `SPLIT=all` to change it; `ARMS="fts5 rerank"` to run only some) with no LLM call, and writes the report to `data/derived/eval/retrieval-<split>.json`. `CHUNK_TOKENS=450` and `CONTEXT_BUDGET=24000` (on it and on `make eval-generation`) score another chunk size or context budget without editing code: `CHUNK_TOKENS` builds `data/derived/edgar_rag-chunks<N>.sqlite` when missing, the report's name gains the setting, and every report records both (use `ARMS=fts5` with `CHUNK_TOKENS`, since the embeddings belong to the shipped index). Its "evidence" column counts the Required Facts whose evidence quote reaches the Answer Context, and the report records Evidence Reached per Required Fact, decided by one function (`edgar_eval.retrieval.evidence_reached`) that the generation harness calls too. For each fact not reached, the report also records its Filing and Section and whether retrieval searched there (the places the Answer Context's Query Scope records in `searched`), and the printout groups the unreached must-state facts as planning misses (the Section plan left the Section out) or ranking misses (searched, but not ranked into the budget). It gates each challenger Arm on it (McNemar's exact test, paired per fact, one-sided, under the selection rules' thresholds; hit@k, recall@k and MRR are reported, not gated on) and screens the challengers: a candidate goes on to paid Answer Calls only if Evidence Reached does not put it behind the shipped choice at one-sided p < 0.20, at most three go on, the most Evidence Reached first and the fewest Source tokens on a tie (ADR 0011). `make eval-arms` and `make eval-settings` apply the screen before their paid runs, and their choice files record it. Tune on dev only; the holdout is scored once per final setup and never used to choose (`docs/evaluation.md`, "The holdout rule"): a run on it reports and decides nothing, and nothing changes after it. Each version's holdout has been scored once on the setup that ships (`docs/evaluation.md`, "The holdout run" for version 1, and "The version 2 holdout run" and "The holdout on the new retrieval" for version 2, scored again after #116 changed the retrieval rules). The harnesses default to version 2, so `SPLIT=holdout` means version 2's holdout: score it again only if a dev choice changes what ships, and never to tune a choice. `make eval-generation SPLIT=holdout` writes `generation-holdout.json`, the earlier run's name, so first keep the earlier reports (as in `data/derived/eval-v2-holdout-issue74/`), then rename the new one `generation-holdout-<suffix>.json` and put the earlier one back: the export reads only the latest holdout run, the suffixed report written last (by its file's modification time, so copy reports with `cp -p`), else `generation-holdout.json`, and the one `retrieval-holdout.json`. The dense and hybrid Arms read chunk embeddings that `make embeddings` builds once into `data/derived/embeddings/` (OpenAI `text-embedding-3-small`; needs `OPENAI_API_KEY`, costs about 35 cents, and resumes if stopped); their question embeddings are cached there too, so reruns make no call. The rerank Arm downloads its cross-encoder once from Hugging Face, pinned to a commit. The `dense-local` and `hybrid-local` Arms read chunk embeddings that `make local-embeddings` builds once into the same directory with `BAAI/bge-small-en-v1.5`, pinned to a commit and run on the CPU (free, no API call, about 30 minutes, resumes if stopped), and embed the question with the same local model. **The one-call rule** (`docs/assumptions.md` #1, 2026-10-17): the Answer Call is a question's only API call, so an Arm that makes another at query time (`query_api_call`: `dense` and `hybrid`, which embed the question with OpenAI) can't ship. It is still scored and reported, as available if the one-call limit is lifted, but the screen never sends it to a paid run and the Arm rule never chooses it; `fts5`, `rerank` and the local Arms are shippable. If a local Arm ships, its embeddings join `make index` and its ranker and packages move into the product. The challengers' packages (numpy, ONNX Runtime, `tokenizers`, `huggingface-hub`) are in the backend's dev dependency group only, and a guard test keeps them out of the product.
