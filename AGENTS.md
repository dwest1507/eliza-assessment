# AGENTS.md

## Agent skills

### Issue tracker

Issues are tracked in GitHub Issues (dwest1507/eliza-assessment) via the `gh` CLI. See `docs/agents/issue-tracker.md`.

### Triage labels

Default labels: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`. See `docs/agents/triage-labels.md`.

### Domain docs

Single-context: one root `CONTEXT.md` plus `docs/adr/`. See `docs/agents/domain.md`.

## Repo layout and commands

- `backend/`: uv-managed Python project holding the `edgar_rag` core package (`src/`), its tests (`tests/`) and the EDA notebook (`notebooks/`). The core package must not depend on a web framework.
- `frontend/`: the Next.js research workspace (npm-managed; Tailwind, AI SDK `useChat`, Vitest). Its server-side route `app/api/chat/route.ts` proxies to the backend's chat API, so the backend URL (`BACKEND_URL`) stays on the server. The conversation lives only in the browser's session storage (`lib/conversation.ts`); the backend is stateless. Each answer's Coverage Gaps show below it as Coverage notes once it is complete, never above it (`components/CoverageGaps.tsx`, ADR 0016). `lib/starters.ts` copies the starter prompts of the Golden Set and the Brief Suite, `lib/chat.ts` copies the prompt's `HISTORY_TURNS` (the proxy sends at most that many earlier messages, and the API rejects more), `lib/followUps.ts` copies the company-name shortening of `_query_scope.py` (`_SUFFIX`, `_THE` and `short_name`, so a suggested follow-up names a Company as the rules match it), and `lib/source.ts` copies the passage gap marker `GAP` of `_repeats.py` (the Sources panel shows it as a break); a test keeps each copy in sync. The "How it works" page (`app/how-it-works/page.tsx`) renders the committed evaluation export, `data/eval-export.json`, typed by `lib/evalExport.ts`: a plain overview first (`components/Overview.tsx`), then "Technical details"; the workspace page reads the same export's coverage grid (`lib/coverage.ts`) for the empty screen's coverage line, which links to that page's "What's covered" list, and its Company Calendars (`companies`) for the side panel's Calendar tab (`components/CalendarPanel.tsx`: a ticker tab per Company any answer's Query Scope named, alphabetical, each showing its `components/CompanyCalendar.tsx`, the component "What's covered" shares). See `frontend/README.md`.
- `data/edgar_corpus/`: the Corpus, read-only (see `data/README.md`). Derived files go in `data/derived/` (gitignored).
- `data/reference/sectors.csv`: the curated Sector table, one row per Company (see `data/README.md`).
- `data/reference/missing_companies.csv`: the curated list of notable Companies not in the Corpus, named as Coverage Gaps (see `data/README.md`).
- `data/eval/golden_set.json`: the Golden Set, the evaluation's labelled questions, including three of the front-end's starter prompts (see `docs/golden-set.md`). Its tests check every label against the Corpus. Version 1's file stays unchanged as a record (a test pins its digest); a harness runs it only when `--golden-set` names it.
- `data/eval/golden_set_v2.json`: Golden Set version 2, holding all 27 of version 1's non-brief cases, rewritten (`docs/golden-set.md`, "The rewritten version 1 cases"), and all six slices of its 53 new cases ("The new cases"): nine multi-Company risk comparisons, then seven risk questions on financials, industrials, energy, health care and consumer staples Companies and two follow-ups, then nine figure trends on Tracked Companies, then four outlook questions and five sector questions on industrials, energy and financials Companies, then eight sector questions on health care, information technology, consumer and communication services Companies and a Coverage Gap case comparing Companies whose latest fiscal years differ, then five Coverage Gap cases (a Snapshot trend, a missing Company, the stale Filing, another periods differ comparison and a covered Company beside a missing one) and three follow-ups: 80 cases. Same schema, every fact tiered, and each case records its split. The split is frozen (`docs/golden-set.md`, "The frozen split"): the 20 new cases with the lowest SHA-256 id digests are `holdout`, every other case `dev`, so 60 dev and 20 holdout, none `pending`; the file lists the holdout ids (`holdout_ids`), the loader refuses any recorded split that disagrees with that list, and a case added later is `dev` unless a new Golden Set version says otherwise. It is the harnesses' default (`DEFAULT_GOLDEN_SET`), and a harness refuses a set with a pending case. The same label tests cover it, plus repeated questions across the three files, figure facts against the SEC company-facts reference (skipped without the cache), the frozen split recomputed from the digests, and its mix of question kinds against ADR 0012 (reported and pinned as frozen, not adjusted). See `docs/golden-set.md`, "Version 2".
- `data/eval/brief_suite.json`: the Brief Suite, the brief's example questions and variants of them outside the dev/holdout split (a must-pass check), with the other three starter prompts. Same schema, no split, every fact tiered; `replaces` names the version 1 case a case was rewritten from, and `variant_of` the brief question a variant varies. The same label tests cover it (see `docs/golden-set.md`, "The Brief Suite").
- `data/eval/judge_study/`: the judge study's labelling sheet and sample, hand-made labels and so committed (see its README). Its verdicts and score stay in `data/derived/judge_study/`.
- `backend/src/edgar_rag/`: `corpus.py` (the Corpus seam), `financial_facts.py` (the Financial Facts seam), `retrieval.py` (the retrieval seam: build the index, prepare an Answer Context), `answer_model.py` (the answer model protocol and the logged Answer Call), `sec_reference.py` (fetches and reads the SEC company-facts evaluation reference), `golden_set.py` (loads and validates both Golden Set versions and the Brief Suite, computes version 1's dev/holdout split, reads version 2's recorded one, checks it against the frozen holdout list and refuses a run while a case is pending, and merges the starter prompts), `paths.py` (the data directory, defined once: every backend module builds its `data/` paths from it, never from its own file location, and a guard test enforces it). The Query Scope parser and follow-up inheritance (ADR 0003) live in the internal `_query_scope.py`, and the topic table, the Filings' own wording that a topic named in a question adds to its search terms (each term naming the Filing phrase it comes from, a test checking each against the full index and the evidence quotes), in the internal `_topics.py`. Standard library only; a guard test enforces it.
- `backend/src/edgar_answer/`: code that needs a provider SDK, kept outside the core package (ADR 0005): `openai_model.py` (the shipped generator), `anthropic_model.py` (the Claude generators, for the generator comparison only) and `ask.py` (`make ask`).
- `backend/src/edgar_api/`: the FastAPI chat API (`app.py`, `make api`), outside the core package: `POST /api/chat` streams the AI SDK UI message stream (Query Scope and Sources as data parts, then the answer), `GET /api/health`. Stateless. `backend/scripts/chat.sh` is the `curl` example.
- `backend/src/edgar_eval/`: the evaluation harnesses, kept outside the core package (ADR 0006): `retrieval.py` (the retrieval harness, `make eval-retrieval`, with its gate and free screen on Evidence Reached), `arms.py` (every retrieval Arm, one marked shipped, each recording whether it makes an API call at query time; each runs the retrieval seam with its own ranker), `rankers.py` (the challenger Arms' rankers: dense, hybrid, cross-encoder), `embeddings.py` (chunk embeddings for the dense and hybrid Arms, `make embeddings`, and, from the local `bge-small-en-v1.5` run by ONNX Runtime, for the `dense-local` and `hybrid-local` Arms, `make local-embeddings`), `metrics.py` (hit@k, recall@k, MRR, McNemar's exact test, the sign test with its one-sided p-values, the bootstrap interval, the case-cluster bootstrap test of ADR 0015, and the judge study's Cohen's kappa, Wilson interval and Fisher's exact test), `selection.py` (the selection rules that pick the Shipped Arm, `make eval-arms`, the generator, `make eval-generators`, and the chunk size and context budget, `make eval-settings`; how the rules differ is stated once, in `RULES`, and the one pair of thresholds every rule uses once, in `AHEAD_P` and `BEHIND_P`; the Arm and settings rules decide Fact Recall fact by fact, ADR 0015; every comparison has a Control Run, and the comparisons of one round share one shipped run and one Control Run), `generation.py` (the generation harness, `make eval-generation`), `rescore.py` (the offline re-score, `make eval-rescore`: it redoes the figure check, the Coverage Gap claims and the uncited claims of saved reports by the harness's own rules, which `generation.py`, `judge.py` and `brief_suite.py` state once), `brief_suite.py` (the Brief Suite run through that harness, `make eval-brief`: several runs a case, a pass/fail verdict per case, and the cost estimate every paid run prints first), `generators.py` (`GENERATORS`, the one table of compared generators with each one's provider and price, and beside it `COMPARISON`, the rows `make eval-generators` runs by default: the answer cost, the harness's answer model, the `make eval-generators` list and the Makefile's API-key check all read them, and the Makefile names no model, so adding, repricing or comparing a generator is one edit), `answer_checks.py` (citation, figure, Coverage Gap and answer-structure checks in code: from prompt v15 the Coverage Gap check scores only the gaps that leave part of the question unanswered, by paraphrase anywhere in the answer, never "periods differ" (`checked_gaps`), and the structure check asks for no closing Coverage note, ADR 0016; and `split_gap_claims`, which keeps a cited sentence stating one of the case's expected Coverage Gaps, other than "periods differ", from Jev: the Coverage Gap check alone scores it, and the case records it in `gap_claims`, ADR 0013's 2026-10-17 note), `judge.py` (Fact Recall and Faithfulness by Jev, pinned in `JEV_MODEL`, a fact counting as stated from `FACT_CUTOFF`), `judge_study.py` (the judge study of ADR 0013: `make judge-study-sample` draws its items from the saved reports with a fixed seed and writes the blind labelling sheet, `make judge-study-judge` has Jev judge them twice and, with `LLM_SPLIT=1`, runs the trial LLM claim split, and `make judge-study-score` scores the verdicts against the labels and compares the two claim splits), `export.py` (the evaluation export for the front-end, `make eval-export`).
- `docs/evaluation.md`: how quality is measured and the scores: each harness's method and its first numbers on dev.
- `docs/findings.md`: EDA findings, each as Finding → Implication → Design decision, ending with recommendations for the retrieval phase.
- `docs/assumptions.md`: every assumption we build under, each marked `confirmed` or `not confirmed` by the Client. `docs/client-email.md` (gitignored, local only) is the email the developer sent the Client about the three that matter most (1, 2 and 3), and the Client's reply confirming them. An agent never sends email to the Client.
- `docs/prompt-iterations.md`: every version of the Answer Call's prompt template. A change to `backend/src/edgar_rag/_prompt.py` bumps `PROMPT_VERSION` and adds an entry.
- `docs/deck.md`: the slide deck, Marp Markdown with speaker notes in HTML comments. Each slide links the documents its numbers come from, and `backend/tests/test_deck.py` checks every figure on a slide appears in one of them; update the slide when an evaluation number changes.
- `docs/adr/`: architecture decisions, numbered `NNNN-slug.md` (0001: the SQLite Financial Facts store; 0008: the Arm comparison and the Shipped Arm; 0009: the generator comparison; 0010: the chunk size and context budget; 0011: the decision thresholds and the Control Run; 0012: Golden Set version 2 and the Brief Suite; 0013: Jev stays the judge, checked by a judge study; 0014: CI runs no paid API and gates retrieval on recorded Floors; 0015: the Arm and settings rules decide Fact Recall fact by fact, amending 0011; 0016: Coverage Gaps are shown by the product as Coverage notes, not recited by the answer, from prompt v15). ADRs 0011 to 0013 are decided and built (each ends with a "Built" note): tiered Required Facts, the Brief Suite, Golden Set version 2 with its split frozen, the measurement fixes, the one-sided thresholds, the Control Run, the Evidence Reached gate and screen, and the judge study, which has been run. The harnesses run Golden Set version 2 by default. Its dev split has been measured: the version 2 comparisons, under ADR 0011's rule, confirm FTS5, `gpt-6-luna`, 600-token chunks and the 32k budget, each noted on ADRs 0008 to 0010, and the Brief Suite passes 1 of 15 cases on that setup (`docs/evaluation.md`, "The version 2 comparisons on dev"). After spec #88's measurement fixes, that setup was run again on dev as the baseline the retrieval work measures against (Fact Recall 0.70, Faithfulness 0.96, the Brief Suite still 1 of 15; `docs/evaluation.md`, "Re-scored on the fixed measurement"). On spec #116's new retrieval (the rule fixes of #119 to #125), the same setup started a new round, with its own shipped run and Control Run, and the Brief Suite was run again (#126): must-state Evidence Reached 85% against 78%, Fact Recall 0.72 and Faithfulness 0.95, and the Brief Suite still 1 of 15, its misses whose evidence never reached the prompt down from 48 to 23 and its generation misses up from 8 to 21 (`docs/evaluation.md`, "A new round on the new retrieval"). In that round the Arm comparison was run again under ADR 0015's fact-level rule (#127): the screen kept only `hybrid-local`, whose answers stated 235 of 316 must-state facts against FTS5's 227 in each of two runs, not ahead (p = 0.180 and 0.189), so FTS5 stays and no local Arm ships (ADR 0008's 2026-10-18 note; `docs/evaluation.md`, "The Arm comparison on the new retrieval"); its reports were lost, and a third run (#129) restored them, 234 facts, p ahead = 0.182. Then the settings comparison was run again on it under the same rule (#129): the screen kept the three 48k budgets, whose answers stated 233 (600 / 48k), 225 (800 / 48k) and 229 (450 / 48k) must-state facts against 227, none ahead, so 600-token chunks and the 32k budget stay (ADR 0010's 2026-10-18 note; `docs/evaluation.md`, "The settings comparison on the new retrieval"). Its reports are in `data/derived/eval/`, #92's are kept in `data/derived/eval-issue92/` and #73's in `data/derived/eval-issue73/`. Its holdout was scored once on the setup before #116, deciding nothing (`docs/evaluation.md`, "The version 2 holdout run"), and, since #116's retrieval rules changed what ships, once more on the new retrieval (#130), deciding nothing: Fact Recall 0.78 against that run's 0.74 and Faithfulness 0.94 against 0.95, must-state Evidence Reached 88% against 82%, 82 of 106 must-state facts stated against 75, read with the 20-case caveat (`docs/evaluation.md`, "The holdout on the new retrieval"). Its reports are `retrieval-holdout.json` and `generation-holdout-new-retrieval.json`; the earlier run's `generation-holdout.json` stays beside it, and both its reports are kept in `data/derived/eval-v2-holdout-issue74/`. The results before them are version 1's, under the rules of 0008 to 0010.

Run everything through the root `Makefile`: `make install` (uv sync and npm ci), `make test`, `make lint`, `make format` (each covers the backend and the front-end), `make eda`, `make sec-facts`, `make index`, `make embeddings`, `make local-embeddings`, `make ask Q="..."`, `make api`, `make eval-retrieval`, `make eval-generation`, `make eval-brief`, `make eval-rescore`, `make eval-arms`, `make eval-generators`, `make eval-settings`, `make eval-export`, `make judge-study-sample`, `make judge-study-judge`, `make judge-study-score`, `make deck` (renders the slide deck with the Marp CLI via `npx`), `make dev` (the API and the front-end together; stops both if either exits).

`make index` rebuilds the retrieval index, `data/derived/edgar_rag.sqlite`, from the Corpus, in 600-token chunks (`CHUNK_TOKENS`; the context budget is `CONTEXT_BUDGET_TOKENS`, 32k, both in `edgar_rag.retrieval` and chosen in ADR 0010). `make ask` answers one question through one Answer Call (it needs `OPENAI_API_KEY` from `backend/.env`, and costs money) and logs it to `data/derived/logs/answer_calls.jsonl`. `make api` serves the same pipeline on port 8000 (`API_PORT` overrides); its tests use FastAPI's test client. Tests never call a provider: they use a fake answer model.

`make eval-retrieval` scores every retrieval Arm on the Golden Set's dev split (`SPLIT=holdout` or `SPLIT=all` to change it; `ARMS="fts5 rerank"` to run only some) with no LLM call, and writes the report to `data/derived/eval/retrieval-<split>.json`. `CHUNK_TOKENS=450` and `CONTEXT_BUDGET=24000` (on it and on `make eval-generation`) score another chunk size or context budget without editing code: `CHUNK_TOKENS` builds `data/derived/edgar_rag-chunks<N>.sqlite` when missing, the report's name gains the setting, and every report records both (use `ARMS=fts5` with `CHUNK_TOKENS`, since the embeddings belong to the shipped index). Its "evidence" column counts the Required Facts whose evidence quote reaches the Answer Context, and the report records Evidence Reached per Required Fact, decided by one function (`edgar_eval.retrieval.evidence_reached`) that the generation harness calls too. For each fact not reached, the report also records its Filing and Section and whether retrieval searched there (the places the Answer Context's Query Scope records in `searched`), and the printout groups the unreached must-state facts as planning misses (the Section plan left the Section out) or ranking misses (searched, but not ranked into the budget). It gates each challenger Arm on it (McNemar's exact test, paired per fact, one-sided, under the selection rules' thresholds; hit@k, recall@k and MRR are reported, not gated on) and screens the challengers: a candidate goes on to paid Answer Calls only if Evidence Reached does not put it behind the shipped choice at one-sided p < 0.20, at most three go on, the most Evidence Reached first and the fewest Source tokens on a tie (ADR 0011). `make eval-arms` and `make eval-settings` apply the screen before their paid runs, and their choice files record it. Tune on dev only; the holdout is scored once per final setup and never used to choose (`docs/evaluation.md`, "The holdout rule"): a run on it reports and decides nothing, and nothing changes after it. Each version's holdout has been scored once on the setup that ships (`docs/evaluation.md`, "The holdout run" for version 1, and "The version 2 holdout run" and "The holdout on the new retrieval" for version 2, scored again after #116 changed the retrieval rules). The harnesses default to version 2, so `SPLIT=holdout` means version 2's holdout: score it again only if a dev choice changes what ships, and never to tune a choice. `make eval-generation SPLIT=holdout` writes `generation-holdout.json`, the earlier run's name, so first keep the earlier reports (as in `data/derived/eval-v2-holdout-issue74/`), then rename the new one `generation-holdout-<suffix>.json` and put the earlier one back: the export reads `generation-holdout.json` first and every `generation-holdout-<suffix>.json` after it, but only one `retrieval-holdout.json`, the latest. The dense and hybrid Arms read chunk embeddings that `make embeddings` builds once into `data/derived/embeddings/` (OpenAI `text-embedding-3-small`; needs `OPENAI_API_KEY`, costs about 35 cents, and resumes if stopped); their question embeddings are cached there too, so reruns make no call. The rerank Arm downloads its cross-encoder once from Hugging Face, pinned to a commit. The `dense-local` and `hybrid-local` Arms read chunk embeddings that `make local-embeddings` builds once into the same directory with `BAAI/bge-small-en-v1.5`, pinned to a commit and run on the CPU (free, no API call, about 30 minutes, resumes if stopped), and embed the question with the same local model. **The one-call rule** (`docs/assumptions.md` #1, 2026-10-17): the Answer Call is a question's only API call, so an Arm that makes another at query time (`query_api_call`: `dense` and `hybrid`, which embed the question with OpenAI) can't ship. It is still scored and reported, as available if the one-call limit is lifted, but the screen never sends it to a paid run and the Arm rule never chooses it; `fts5`, `rerank` and the local Arms are shippable. If a local Arm ships, its embeddings join `make index` and its ranker and packages move into the product. The challengers' packages (numpy, ONNX Runtime, `tokenizers`, `huggingface-hub`) are in the backend's dev dependency group only, and a guard test keeps them out of the product.

`make eval-generation` answers the same split through real Answer Calls and scores the answers (checks in code, Jev judgments, cost and latency), writing `data/derived/eval/generation-<split>.json`. It needs `OPENAI_API_KEY` and `JEV_API_KEY` from `backend/.env` and costs money (about $0.25 per dev run on version 2's 60 cases, Jev included), so run it only when a change to the prompt, retrieval or generator needs scoring. `ARM=dense` answers through another retrieval Arm, writing `generation-arms-<split>-<arm>.json`. `make eval-brief` runs the Brief Suite through the same harness: each case answered 5 times (`RUNS=` changes it; `MODEL=`, `ARM=`, `CHUNK_TOKENS=` and `CONTEXT_BUDGET=` as for `make eval-generation`), passing when every must-state Required Fact is stated in at least 4 of the 5 runs and no run has a Contradicted Claim, reported case by case with each fact's Evidence Reached, and written to `data/derived/eval/brief-suite.json`. It needs the same keys and costs money (about $0.40 for its 75 Answer Calls with `gpt-6-luna`, Jev included); like every generation run it prints its estimated cost before the first Answer Call. `make eval-rescore` re-scores saved reports from their stored answers, in place (`edgar_eval.rescore`). By default it re-scores only the current round's reports: the shipped run (`generation-<split>.json`), the Control Run (`generation-control-<split>.json`) and the Brief Suite (`brief-suite.json`), with `SPLIT=` choosing the split. Other reports, such as #73's comparison reports, which stand as recorded, are re-scored only when named (`REPORTS="generation-dev-claude-haiku-5-5.json"`, a path or a name in `data/derived/eval/`), and `REPORTS=all` re-scores every saved generation and Brief Suite report. Each generation report is re-scored against the Golden Set version it records (version 1 when it records none). The figure check is redone with each Answer Context prepared again, at the context budget the report records (from `data/derived/edgar_rag-chunks<N>.sqlite` for a report of another chunk size, refusing it when that index is missing, and refusing a case whose Sources no longer match). Jev's stored verdicts on expected Coverage Gap sentences are dropped, in a Brief Suite report from every run, and Faithfulness, Contradicted Claims and the passes that rest on them are recomputed. The stored uncited claims that the current claim split of each stored answer no longer makes are dropped, and Faithfulness is recomputed. It never adds a claim the split newly makes: #111's tightened rule makes 4 new uncited claims in #73's comparison reports, and even `REPORTS=all` leaves them out. It makes no Answer Call and no Jev call, so it is free and allowed on the holdout, since it fixes a measurement and changes no choice. `make eval-arms` runs the retrieval harness first (free, writing `retrieval-<split>.json`), answers the split through the Arms its screen keeps, and applies the selection rule (`edgar_eval.selection`, ADR 0011 as amended by ADR 0015: a challenger ships only if it is ahead on Fact Recall fact by fact at p < 0.10, the must-state facts stated summed over the paired cases and tested by a one-sided case-cluster bootstrap, 10,000 resamples of whole cases with a fixed seed, and behind on no guardrail, Fact Recall case by case by the one-sided sign test, Faithfulness, Coverage Gaps or Contradicted Claims, at p < 0.20; each comparison also splits the facts stated by where their evidence reached; the cheapest qualifying challenger wins; each score also reports the mean paired difference with a 95% bootstrap interval, fixed seed, shown but not decided on; version 1's choice files, made at two-sided p < 0.05, are records and are not recomputed), writing `arm-choice-<split>.json`; it costs about $0.25 per Arm on dev. Every comparison also has a Control Run, the shipped choice run again: if it comes out ahead of the shipped run on one of the rule's ahead metrics, the choice is inconclusive and the shipped choice stands. `make eval-arms`, `make eval-settings` and `make eval-generators` share one round's shipped run (`generation-<split>.json`) and Control Run (`generation-control-<split>.json`), reusing them while the code (a digest of `backend/src/`), prompt and Golden Set version the reports record are unchanged and running them first otherwise, so a round's first comparison costs about $0.50 more. `make eval-settings CANDIDATES="450:32000 600:48000"` screens the shipped setting and each named chunk size and context budget with the retrieval harness first (free, writing `retrieval-<split>-chunks<N>-budget<B>.json`), answers each setting the screen keeps and applies the Arm rule, writing `generation-<split>-chunks<N>-budget<B>.json` and `settings-choice-<split>.json`. `MODEL=claude-sonnet-5-5` answers with another generator (a model's provider, and so the key it needs, `OPENAI_API_KEY` or `ANTHROPIC_API_KEY`, comes from `edgar_eval.generators.GENERATORS`; a model not in that table is refused), writing `generation-<split>-<model>.json`. `make eval-generators` answers the split with the default comparison, `COMPARISON` in `edgar_eval.generators` (`gpt-6-luna` and `claude-haiku-5-5`, version 2's), and applies the generator rule (a challenger replaces `gpt-6-luna` only if ahead on Fact Recall or Coverage Gaps and behind on none of Fact Recall, Faithfulness, Coverage Gaps and Contradicted Claims, at the same thresholds), writing `generator-choice-<split>.json`; it costs about $0.37 on dev for Claude Haiku 5.5's run. `MODELS="..."` names other generators from the table instead (`gpt-6-luna` always runs, as the shipped one), and `MODELS=` (empty) runs every one (`edgar_eval.selection generators --all`), version 1's four included, for about $6 on dev; the version 1 generators stay in the table so their reports still price. Jev stays pinned to an exact version, never `jev-latest`; a new version is a deliberate change that re-baselines every score.

`make eval-export` writes the latest reports of a split (`SPLIT=`, dev by default) and the Corpus coverage grid to `frontend/data/eval-export.json`, which the "How it works" page renders: retrieval gated on Evidence Reached with the screen and each Arm's shippability, the round's shipped run beside its Control Run, the Arm and settings comparisons (`arm-choice-<split>.json`, `settings-choice-<split>.json`: each challenger's and the Control Run's per-case sign tests and, for a choice file made under ADR 0015, its fact-level test, `stated_facts`, and its split by evidence status, `by_evidence`; a choice file made before ADR 0015, such as #73's, exports with those fields null and the page shows it as decided case by case, standing as recorded), the generator comparison and the challenger runs it names, the Brief Suite's verdicts (`brief-suite.json`) and, beside dev, the holdout's reports, and two sections the front-end reads for its Companies: `companies`, each Company's Company Calendar (ticker, name, Sector, coverage class, fiscal year end, and every fiscal quarter and year from its first Filing to its latest with its calendar months, its Filing or none, and, for a Tracked Company, its revenue Financial Fact read by the Financial Facts seam, a fourth quarter derived as the 10-K's year less its three 10-Qs and marked as derived; a Snapshot Company has none), and `missingCompanies`, the curated list of notable Companies not in the Corpus. It runs the retrieval harness when its report is missing, never the generation harness. It describes Golden Set version 2 (`--golden-set` names version 1's file, which still exports against version 1's reports, as in `data/derived/eval-golden-set-v1/`), reads a generation report only when the round or a comparison names it, and refuses a dev or holdout report that records another Golden Set version rather than mix the two. The export is committed: regenerate it with `make eval-export`, never edit it by hand, and keep its shape in step with `frontend/lib/evalExport.ts` (the type check fails when they drift).

`make judge-study-sample` draws the judge study's items (ADR 0013) from every saved generation and Brief Suite report: 150 (answer, Required Fact) items, using only the rewritten one-claim facts of Golden Set version 2 and the Brief Suite, never version 1's compound ones, and 200 (claim, cited Sources) items re-split from the stored answers, over-sampling uncertain probabilities, unsupported and contradicted verdicts, and every generator. It draws with a fixed seed (`SEED=` changes it) and writes `data/eval/judge_study/sheet.md`, the blind labelling sheet the developer fills in, with no Jev verdict or probability in it, and `sample.json` beside it, which records why each item was drawn and is not read while labelling. Both are committed, beside the Golden Set, since they hold hand-made labels; the developer commits the labelled sheet. No drawn sheet is committed until version 1's cases are rewritten. It calls no provider and is free; running it again keeps every label entered, and refuses to drop a labelled item. See `docs/evaluation.md`, "The judge study's sample".

`make judge-study-judge` has Jev judge every sampled item twice (`REFERENCE=1` adds Claude Haiku 5.5 once, as a reference judge; `LLM_SPLIT=1` adds the trial LLM claim split, Claude Haiku 5.5 splitting each sampled answer into one-claim statements, cached per answer in `data/derived/judge_study/llm_split/`, which Jev judges once; it lives in the study only, never in the generation harness), printing the estimated cost first; it needs `JEV_API_KEY` (and `ANTHROPIC_API_KEY` for the reference or the split) and costs money, so run it only with the developer's approval. It writes `data/derived/judge_study/verdicts.json` (gitignored, since it can be regenerated), apart from the sheet, with a verdict or a recorded failure for every item in every run. `make judge-study-score` is free: it scores those verdicts against the sheet's labels (accuracy and kappa, the share of bad claims called supported, error by generator, run-to-run agreement, the fact cut-off sweep, ADR 0013's revisit trigger, the early-stopping rule and, when the split was run, which split's claims agree better with the labels, answer by answer) and writes `score.json`; it refuses while items are unlabelled unless the stopping rule is met or `PARTIAL=1`. The fact cut-off is `FACT_CUTOFF` in `edgar_eval.judge`, 0.6, set by the study, and every generation report records it. The study has been run (2026-10-17): its labels, in `data/eval/judge_study/`, are Claude's (`claude-opus-5-5`), made on the developer's delegation, so it measures Jev's agreement with Claude, not with a human; never describe them as the developer's. See `docs/evaluation.md`, "Judging and scoring the judge study".

`make sec-facts` caches the SEC XBRL company-facts data (an evaluation reference for Financial Facts, never an answer source) in `data/derived/sec_companyfacts/`; `make eda` runs it when that cache is missing. The SEC requires a User-Agent with a contact email, read from the `SEC_USER_AGENT` environment variable, which the Makefile loads from `backend/.env`.

Environment files are per app: each app has a gitignored `.env` and a committed `.env.example` with placeholders only, and the app's `.dockerignore` keeps `.env` out of images. The developer fills in `.env`; an agent never creates or edits it and never writes a real value into code, the Makefile, docs, tests, notebook outputs, `.env.example` files or commit messages. A new variable goes into that app's `.env.example` with a placeholder.

The notebook source of truth is `backend/notebooks/eda.py` (jupytext percent format). `make eda` executes it and writes the paired `eda.ipynb` with outputs; commit both and never edit the `.ipynb` by hand.
